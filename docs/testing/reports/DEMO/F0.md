## What F0 does

| Event | Spoken |
|---|---|
| Camera absent at start-up, or lost while running | "Critical Error: Camera cannot be reached" at once (inside the loss handler, not after the teardown), then every 10 s from the start of each sentence |
| The vision pipeline runs on a camera again | The missing sentence stops repeating; 1 s later, if the camera has not failed again, it is cleared and "Camera has been reconnected" is said once |

Since F1 to F4 these are also failsafe alerts: spoken with the speech switch off (D41), and each missing sentence
comes with the camera *beep beep* (F4).

## What I reviewed

- The whole diff of `pipeline/app.py` against the baseline (181 lines; 8 of them are F4's, the rest F0's) and
  the brief's ten acceptance criteria, mapped to tests (next section).
- **Every route into "camera missing" reaches a hook** (the brief's risk R2). `CAMERA_LOST` is set only in
  `_on_camera_lost`. `CAMERA_WAITING` is set in `_wait_for_camera` (the end of the loss teardown; a mode-switch
  rebuild that finds the node gone; and `_back_to_waiting`, after a start that could not use the camera) and in
  `_start_without_camera`. All four call `_raise_camera_missing`. A start where another element fails
  (`START_FAILED`) shuts down as it always did; that is not a missing camera.
- **The return cannot be missed.** `_rebuild_pipeline` and `trigger_rebuild` refuse to run while the camera
  state is not OK, so vision can only restart after a loss through `_start_on_camera`, which announces the
  return. (`_rebuild_on_camera` does not announce, correctly: it only runs when the camera was never reported lost.)
- **The 1 s confirmation window is justified.** A camera held by another process fails a few milliseconds
  after the pipeline reaches PLAYING ("Device is busy"). Without the window the wearer would hear "Camera has been
  reconnected" and then the missing sentence again. The Developer's device log shows it: 3 'is busy' failures in one
  28 s hold. A test pins the behaviour, and removing the window (mutation 10 below) is caught.
- **No Hailo or GStreamer call is added** (AGENTS.md Rule 6). The hooks talk to the alert scheduler only. The one
  non-scheduler call is `GLib.timeout_add` for the confirmation, a one-shot timer on the main loop that changes no
  pipeline state; the same call and thread rule as the rebuild scheduling already in this file
  (`GLib.timeout_add(delay_ms, self._rebuild_pipeline)`). A test asserts the hooks make no GStreamer call and
  that one call takes well under 50 ms.
- **Two comments were out of date and are fixed (comment-only change, `pipeline/app.py`).**
  - The block comment said whether the alerts override the speech switch is "the user's open question D-15" and
    the worker drops them while speech is off. It was decided and built (F1, D41): they are spoken anyway.
  - A section comment said "nothing here ... plays a motor pattern". Since F4 the missing-camera alert asks for
    the camera pattern (nothing in app.py touches the motors).

## Behaviour to know

- **The return sentence waits for an utterance in progress.** Clearing an alert never cuts a sentence being said, so
  "Camera has been reconnected" follows the end of "Critical Error..." (the tests measure 1.4 to 2.5 s).
- **A missing sentence that never started is withdrawn at the return.** If the speech channel is busy with a long
  announcement for the whole loss, only "Camera has been reconnected" is said. Pinned by a test; rare.
- **A camera gone for under about a second** is not announced as back (the window); the missing sentence goes on.
- **The camera has dropped on its own once, with no unplug (2026-10-15).** The device-level checks look at every
  camera episode the program logs, not only the ones the test caused. Nothing was run on the device this session, so
  nothing new was seen.
