# F7 · An alert in progress finishes (D-16)

2026-10-19, one session (Opus). The user's decision D-16 (2026-10-18, option b): "let an alert in progress finish
(2 to 3 s) before an urgent object warning can cut it." No git writes. **Not heard on the device yet**; the demo
rehearsal (F8) exercises it whenever an alert falls due while objects are being announced.

## What was wrong (the Tester's finding F-1 on T-00a, 2026-10-18)

Two separate problems, both in what happens when an urgent object (a car ahead, say) is announced again and again:

1. **The speech worker let any urgent item cut whatever it was saying**, a failsafe alert included. The alert was
   then said again, and cut again by the next urgent warning.
2. **The alert scheduler offered an alert only when the speech worker was idle.** Urgent warnings arriving faster
   than a phrase lasts (the detection callback offers one per frame for an urgent object that stays in view) cut
   each other, so the worker was never idle and the alert was **never offered at all**: the wearer was never told
   that, say, the vibration board had stopped working.

## The rule now

**Whatever is being said finishes; a due failsafe alert goes next, ahead of new object warnings.**

| Situation | Before | Now |
|---|---|---|
| An alert is being said; an urgent warning comes | the warning cuts it; the alert is said again later | the alert finishes (2 to 3 s), then the warning |
| An alert falls due while a warning is being said | waits for the worker to be idle (never, under a stream of urgent warnings) | waits in the slot and is said as soon as that phrase ends; it cuts nothing, and no later warning gets ahead of it |
| An alert falls due while a mode announcement is being said | waits for the end | the same (unchanged) |
| A mode announcement comes while an alert is being said | cuts it; the alert is said again | the same (unchanged: it is the wearer's own switch) |

## What changed (named, AGENTS.md Rule 3: the speech worker's preemption check and the scheduler's offer rule)

| File | Change |

Without the scheduler (`user_data.alerts` absent) the rule is `preempts()` exactly as before. `core/priority.py` is not changed. |

| `tests/test_alerts_speech.py` | The same through the real speech worker: the old "cut by an urgent detection" test now uses a mode announcement (which still cuts), and a new test shows the urgent detection waiting. |

**Found on the way:** the first version also offered the alert while a *mode announcement* was being said. The
randomised runs caught it ("tie" path, seed 2: a once-only alert never said in 330 s). A mode announcement offered
while the alert waits in the slot replaces it (the mailbox keeps the newer of two equal priorities), and a burst of
them kept the alert out. Behind an announcement it now waits for the end, as before; announcements are short.

  | Object warnings (phrase 1.2 s) | Before | Now |

  | urgent, every 0.8 s (each cuts the last) | never heard | max 1.07 s |
  | urgent, every 0.3 s | never heard | max 1.27 s |
  | urgent, every 0.1 s (one per frame) | never heard | max 1.30 s |

- **New:** an urgent detection waits for an alert in progress (the speech model and the real worker); an alert due
  during an urgent warning waits for its end and goes next; urgent warnings that cut each other cannot keep an alert

## What it costs the wearer

When an alert falls due while an urgent object is being announced, the next announcement of that object waits for
the alert: at most the phrase in progress (about 1.2 s) plus the alert (2 to 3 s). Alerts repeat every 10 s (camera,
when there are no detections anyway), 30 s (glasses board) or 5 minutes (control panel), so this happens at most
once per repeat. That is the trade D-16 chose.
