Also true now, and tested:

- **Glasses return while the earphones are out:** "Vibration is working again", not "Everything is
  connected". This was the open case F2 left (the earphones have no spoken alert). The silent alert
  stands for them in `alerts.raised()`, so `reconnect_text()` sees them.
- **Both out, then both back:** the glasses give "Vibration is working again"; the earphones, last,
  give "Everything is connected".
- **No setting changed:** only reads; the tests compare `config.snapshot()` before and after.
- **Cost:** one reading is a listing of `/proc/asound` (4 small directories): **134 µs** on this Pi, so
  once a second is about **0.013 % of one core**. It runs in its own thread and never touches the
  camera pipeline.

## How the earphones are told apart (the sources disagree)

- **DEMO-TRACK F3** says: "the same rule as `usb_sim.py`'s `earphones()`", which reads
  `/sys/class/sound`: a USB device with a sound card that can play and no video node.
- **D-18 and REQUIREMENTS (section 8)** decided something else: a `/proc/asound/cardN` that has a `usbid`
  file and a `pcm*p` (playback) entry. Plain file reads.
- **The code supports D-18.** It is the decision already recorded and approved, and it needs no sysfs
  path walking. The two give the same answer on this Pi (measured today): `card2` (SPACETOUCH, `0666:0880`,
  has `usbid` and `pcm0p`) is the earphones; `card3` (the Arducam microphone, `0c45:0261`, `usbid` but
  capture only) and the two HDMI cards (`pcm0p` but no `usbid`) are not. They differ only for a USB
  device that has both a video node and a speaker, which this project does not have.
- **Not confirmed yet:** that `usb_sim.py detach earphones` (which sets the USB `authorized` flag to 0) makes
  the card vanish from `/proc/asound`, as a real unplug does. D-18 expects it. The device check below reads
  `/proc/asound/cards` during the detach to settle it.

## Found on the way

- **`tests/test_main_startup.py` pins the worker list.** `main.py` starts a fixed list of workers and two
  older tests (T-03b) pinned it as `["tts-worker", "alert-scheduler", "serial-writer"]`. Adding the
  earphones worker is deliberate, so both assertions now end with `"earphones-watch"`. The first full run
  after the change showed exactly these two failures and nothing else.
- **The state moves only after the action worked.** `EarphonesWatcher` commits "lost" or "back" after
  `earphones_lost()` / `earphones_back()` succeed, so a scheduler error is retried at the next reading
  instead of leaving the earphones marked lost with no alert. (A mutation check caught a first test that
  covered only the start-up branch.)

## Not tested, and known limits

- **Nothing on the device yet.**
- **Boot order.** `second-vision.service` starts after `hailort.service` and the user's audio session, with
  no ordering on the USB sound card. If the app ever started before the card is up, the wearer would get one
  loss pattern and then "Everything is connected". USB audio normally enumerates well before the service
  starts, so no start-up grace was added without evidence. A reboot with the earphones plugged in would show
  it; it is not part of this check.
- **The returned earphones may need a moment before they play.** The sentence is offered 1 to 2 s after the
  card appears. If the device check shows "Everything is connected" cut off or missing while the *beep beep*
  still comes, add a short wait before the sentence.
- **The pattern costs the wearer their depth vibration for 2.25 s** (the pattern's length) every 30 s while
  the earphones are out and detection is on. That is F1's design, not new.
- **If the glasses board is not answering,** patterns are dropped (F1). The earphones' pattern is then tried
  again 30 s later; the sentence on return is unaffected.
- **A USB sound card that appears with no playback stream yet** counts as missing until it has one.

## Device check (batched session)

The boot service holds the camera and the Hailo chip, so it must be stopped first; the user stops it or
approves it. Check `systemctl is-active second-vision` and `pgrep -af "Parallel-Depth|pytest"` first.
Run the program from this worktree:

```bash
cd ~/Projects/Second-Vision/worktrees/kenth && scripts/sv-main.sh 2>&1 | tee docs/testing/reports/DEMO/evidence/F3-device.log
```

1. With everything running and the DETECT rocker on: `sudo -n .claude/tools/usb_sim.py detach earphones --for 70`.
   - In another shell, `cat /proc/asound/cards` should lose the SPACETOUCH card within a second or two. If it
     does not, tell the session: the presence rule then needs another look.
   - Expect *strong weak* ×3 on all three motors about 1 to 2 s after the detach, and **no speech**. Again at
     about 30 s and 60 s.
2. At about 20 s switch DETECT off: no more patterns.
3. When the 70 s are up: *beep beep*, then "Everything is connected" **in the earphones**. Note if the sentence
   is cut off or missing.
4. Repeat with `--for 20` and DETECT off from the start: one pattern only.
5. Repeat with the vibration switch off: the patterns still come.
6. One real unplug of the earphones' cable, and plug back.
7. With the camera also out (`usb_sim.py detach camera --for 40`), put the earphones back first: expect
   "Earphones connected", not "Everything is connected".
8. Write in `F3.md` what was heard and felt. The log lines to look for are `[EARPHONES] not found`,
   `[ALERT] raised 'earphones-missing' ... (silent)`, `[PATTERN] playing 'earphones'`,
   `[EARPHONES] found again`, `[PATTERN] playing 'reconnect'` and `[ALERT] raised 'earphones-reconnected'`.
