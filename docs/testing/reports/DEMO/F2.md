What the wearer gets:

| Event | Spoken | Felt |
|---|---|---|
| Board stops answering (2.5 s without an acknowledgement), or is absent at start-up | "Vibration is not working" at once. Again every 30 s while depth is on (mode `depth` or `both`), once while it is off. Switching depth off mid-run stops the repeats (W-11). | Motors stopped (as before) |
| Board answers again | That alert stops (one already being said finishes). Then once: "Everything is connected", or "Vibration is working again" while another part is still missing (D-17). | The reconnect *beep beep* (F1), even with the vibration switch off, at max(knob, 30 %) |

**D-17, done carefully:** "still missing" means one of the `MISSING_ALERTS` names (camera, glasses) is
raised. It does not mean everything in `alerts.raised()`, because the scheduler keeps a spoken once-only
sentence raised until it is cleared. "Camera has been reconnected", for example, stays raised until the
next camera loss, and it would wrongly block "Everything is connected". For the same reason the glasses'
own "back" sentence is cleared at every loss, or a second return with the same text would be silent.

## Found on the way

**The panel never sends `depth_enabled` or `detection_enabled`.** It reports its DETECT and DEPTH rockers
only as the mode line (`M:both`, `M:depth`, `M:detection`, `M:none`; `firmware/control-panel/PROTOCOL.md`).
So `config.depth_enabled` is True for the whole run, whatever the rocker says. A repeat rule written as
`config.get("depth_enabled")`, as the scheduler's docstring example suggested, would never stop repeating.
`depth_on()` reads `pipeline_mode` instead. **F3 needs the same for "detection on"** (mode `detection` or
`both`).

## Not tested, and known limits

- **Nothing on the device yet.**
- **A port that could not be opened is not opened again.** The alert then lasts the whole run, with no
  return. This doesn't matter for the glasses board, which is on the GPIO UART (`/dev/serial0`): that
  device always exists, so pulling the cable shows up as "not answering", which does recover. A
  USB-serial board would need the port reopened; not done.
- **The panel and earphones are not part of D-17 yet.** F6 adds the panel's missing alert to
  `MISSING_ALERTS`. The earphones have no spoken alert (nothing to speak through), so F3 must give
  `reconnect_text()` another way to know they are missing.

## Device check (batched session)

The boot service holds `/dev/serial0`, so it must be stopped first; the user stops it or approves it.
Run the program from this worktree, which needs the camera and the Hailo chip free:

```bash
cd ~/Projects/Second-Vision/worktrees/kenth && scripts/sv-main.sh 2>&1 | tee docs/testing/reports/DEMO/evidence/F2-device.log
```

1. With all of it running, unplug the glasses board's cable (or its power).
   - Expect "Vibration is not working" about 2.5 s later.
   - With the DEPTH rocker on, it repeats every 30 s.
2. Switch DEPTH off: no more repeats.
3. Plug the cable back in.
   - Expect *beep beep* on all three motors, then "Everything is connected".
4. Repeat with the vibration switch off: the *beep beep* still comes.
5. Write in `F2.md` what was heard and felt. The log lines to look for are `[SERIAL] ESP32 stopped
   acknowledging`, `[ALERT] raised 'glasses-missing'` and `[PATTERN] playing 'reconnect'`.
