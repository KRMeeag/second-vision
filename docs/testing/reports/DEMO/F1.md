The patterns (duty at full strength, all three motors). The timings and `WEAK_DUTY` are first
guesses; the device check sets them.

| Pattern | Steps | Length |
|---|---|---|
| reconnect *beep beep* | 255 for 0.15 s, off 0.15, 255 for 0.15, off 0.30 | 0.75 s |
| camera *beep beep* (slower) | 255 for 0.40 s, off 0.20, 255 for 0.40, off 0.30 | 1.30 s |
| earphones *strong weak* ×3 | (255 for 0.25 s, 150 for 0.25, off 0.25) × 3 | 2.25 s |

How the strength knob scales a pattern: **plain multiply**, the user's choice in this session
(2026-10-18): duty × max(knob, 0.30). With the knob at or under 30 %, strong = 76 and weak = 45.
**Risk to check on the device:** `core/haptics.py` assumes the motors start at duty 90 (`PWM_FLOOR`,
never measured), so at 30 % a pattern may be faint or not felt. The other option offered was "the
knob on the felt range" (90 + 165 × level × knob), which would make it about 140/110 at 30 %.

Use from F2, F3 and F4: `user_data.patterns.play(PATTERN_RECONNECT)` (or `PATTERN_CAMERA`,
`PATTERN_EARPHONES`), from any thread. Nothing calls it yet.

## Behaviour to know

- **Start delay:** a pattern starts at once while depth frames flow. With depth off it starts within
  0.25 s, the worker's queue wait.
- **Depth pause:** while a pattern plays, the wearer gets no depth vibration, for 2.25 s at most
  (earphones). A ground-hazard pulse still gets through, and can shorten one step by its 150 ms.
- **Queueing:** patterns play one at a time, each to the end. Asking for one that is already
  waiting does nothing.
- **Board not answering:** patterns are dropped, not kept. F2 plays reconnect when the board returns.
- **Not changed:** an alert can still be cut. A mode announcement, or an urgent detection with speech
  on, cuts it as before, and it is spoken again afterwards. Letting an alert finish first is F7.
- **No settings written:** the switches and knobs are only read. The tests compare
  `config.snapshot()` before and after.

## Device check (batched session)

The service must be stopped first, because it holds the glasses board's port; the user stops it or
approves it. This plays every pattern at knob 1.0 and then at knob 0 (the 30 % floor), through the
real serial worker:

```bash
PYTHONPATH=src my_hailo_env/bin/python - <<'EOF'
import queue, threading, time
from types import SimpleNamespace
from second_vision.core.config import SystemConfig
from second_vision.core.haptic_patterns import PatternPlayer, PATTERNS
from second_vision.workers.serial_worker import serial_worker
cfg = SystemConfig(); cfg.update(serial_port="/dev/serial0")   # sv-main.sh's SERIAL_PORT default
ud = SimpleNamespace(serial_queue=queue.Queue(maxsize=10), shutdown_event=threading.Event(),
                     patterns=PatternPlayer())
t = threading.Thread(target=serial_worker, args=(ud, cfg), daemon=True); t.start()
time.sleep(1.5)
for knob in (1.0, 0.0):
    cfg.update(motor_strength=knob)
    for name in PATTERNS:
        print(f"knob {knob}: {name}", flush=True); ud.patterns.play(name)
        while ud.patterns.busy(): time.sleep(0.05)
        time.sleep(1.5)
ud.shutdown_event.set(); t.join(2)
EOF
```

Expected: "UART Connection to ESP32 is WORKING!", then six patterns. Note for each one whether it was
felt and whether the patterns can be told apart. If the 30 % patterns are not felt, the fix is one
line in `_play_pattern_step`, the scaling question above.
